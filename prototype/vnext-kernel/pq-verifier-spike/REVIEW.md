## A. Findings, ranked by severity for the stated consumer

(Consumer: Gen-2 kernel, `IKernelPQVerifier.verify(bytes32 digest, bytes publicKey, bytes signature) view returns (bool)`, PQ a mandatory conjunct on every authority predicate, verifier revert = denial, kernel commits to `keccak256(publicKey bytes)`: `prototype/vnext-kernel/generation-2/contracts/VaultKernelGen2Prototype.sol:474`, `:746`, `:749`, `:932`.)

### A-1  The degenerate-key class is wider than the package's gate, and the package's proposed remedy (proof of possession) does not remove it — HIGH (design-level) — CONFIRMED

- Where: `test/Adversarial.test.ts:181-208` (the only gate tested is `pk.slice(32).every(b => b === 0)`, :204); `UNRESOLVED.md:12` (U-3: "refuses t1 = 0 (trivial) and a proof of possession"); `PUBLISHER_BINDING.md:45-48` (rule 3: refuse unless `t1 != 0` "and, if the owner so decides, a proof-of-possession signature ... The degenerate-key forgery is thereby excluded at the only layer that can see it") and `:63` (A + C: "a possession signature (so the user holds the secret of pk, excluding degenerate and borrowed keys)").
- What is wrong: (i) `pk = rho || 0xff^1920` is a degenerate ML-DSA-65 key with a public secret `(s1, s2, t0) = (0, -1, 0)` (check 4; `1023 * 2^13 = q - 1` depends only on q and d, which ML-DSA-65 shares with -44, so the Fireblocks result carries over). The `t1 == 0` gate does not refuse it, and neither would any "low weight / near zero" rule. Fireblocks' measured result (`C:/dev/GEN2-PQ-FEASIBILITY-1-work/src/fireblocks-main/docs/SAFETY.md:328-340`) is that the cheaply forgeable set is roughly `|centred_lift(t1)| <~ gamma2/4` per coefficient, widened by message grinding. (ii) A proof of possession is a signature check, and on a degenerate key a signature is exactly what is free: the package's own forgery (`Adversarial.test.ts:186-196`) signs an arbitrary digest with no secret, so it answers any PoP challenge. `SAFETY.md:374-396` states this explicitly ("A key-free-forgeable public key does not have NO owner: it has EVERY owner") and demonstrates it; `SAFETY.md:398-424` shows a proof of knowledge of `(s1, s2)` fails the same way. The only complete criterion is binding the key to its KeyGen seed xi (`SAFETY.md:342-368`); the only registrar-evaluable floor is the centred-lift criterion (`SAFETY.md:303-340`). The package cites the Fireblocks repository but adopts neither and recommends the one that does not work.
- Failure scenario: a user's wallet software (or a supply-chain-compromised client) hands the registrar a degenerate pk; registration passes the `t1 != 0` gate and the PoP; every later `IKernelPQVerifier.verify(digest, pqKey, pqSig)` (`VaultKernelGen2Prototype.sol:749`) is satisfiable by anyone, and the rotation PoP (`:932`) too. Under the package's own threat model (a quantum adversary holding the ECDSA material, `UNRESOLVED.md:4-6`) the mandatory PQ conjunct then protects nothing, and the on-chain record looks like a healthy registration.
- Would the evidence package catch it: no. No fixture carries `t1 = 1023` or any non-zero degenerate t1; Wycheproof's `ZeroPublicKey` group (51 vectors, 1 valid) is the `t1 = 0` instance only. On-chain acceptance of the 0xff key is PLAUSIBLE (not run here): the verifier agreed with `@noble` on all 292 vectors including the `t1 = 0` forgery and implements the same arithmetic.

### A-2  Soundness rests on a 19,617-byte binary nobody can regenerate; the evidence for it is behavioural only — HIGH (open; U-2 records it, severity restated) — CONFIRMED as an evidence gap

- Where: `ZKNOX_dilithium65.sol:172-175` (the verdict is `keccak256(SHAKE256(mu || w1, 48)) == keccak256(c~)` with SHAKE256 computed inside the helper); `ZKNOX_shake_fast.sol:198-217` (for every input except exactly 800 bytes, padding, absorb AND squeeze all run inside the helper; the Solidity glue at `:39-188` is used only for 800-byte preimages and for the SampleInBall fallback); `vendor/fireblocks-evm-ml-dsa-verifier-cca262b5/helpers/README.md:25-38`; `PROVENANCE.md:43-47`; `UNRESOLVED.md:11`.
- What is unproven: that `f1600_core.hex` is Keccak-f[1600] on every state. The evidence is 50 permutations + 37 batched SHAKE256 messages agreeing with `@noble/hashes` (`Adversarial.test.ts:268-327`), 292 vectors, and the dispatcher rebuild. A permutation correct except on a hidden input class is invisible to all of it. This is the largest trust assumption in the TCB and it is shared with the only other public EVM ML-DSA verifier (`UNRESOLVED.md:15`, U-6), so a two-member admissible set would not diversify it.
- What would close it: the core is straight-line (`build_f1600_batch.py:6-9`), so a bit-level equivalence proof of the 19,617 bytes against a reference Keccak-f[1600] is tractable; or regenerate it from a preserved generator.

### A-3  Handle and blob binding: the verifier binds a handle to nothing canonical, and the census missed at least one more unread region — MEDIUM (design-level; U-4 records most of it) — CONFIRMED

- Where: `ZKNOX_dilithium65.sol:133-143` (`_readPubKey` loads 40 bytes at `pk.offset` with no `pk.length` check; a shorter `pk` reads the adjacent calldata tail, a longer one ignores the rest); `ZKNOX_dilithium65_core_packed.sol:76-143` (`readPubKeyPacked65` checks shape only: offsets in range, `[32]` polynomial length words, `tr` length 64); `:139` (`if (h == 0) tr = trh;` — half 1's `tr` is validated for length and its content never read); `:103-105` (overlapping or shared polynomial offsets inside a blob are accepted); `:278-281` (matvec trusts the shapes; field VALUES are never range-checked, so a blob with fields >= q is consumed by lane arithmetic whose bound argument at `:20-23` assumes fields < q).
- Consequences for the consumer: `keccak256(pqKey)` (`VaultKernelGen2Prototype.sol:474`, `:746`) over a 40-byte handle commits to two addresses whose code is immutable (SSTORE2 `0x00` prefix, `vendor/sstore2-0a28fe61/contracts/SSTORE2.sol:26`; no selfdestruct path), so it IS a sound commitment to blob bytes — but to no canonical FIPS key, no seed and no user. A mis-published or corrupted blob is a silently different key (recorded in `results/adversarial.json`), and because revert/false = denial, a vault whose committed handle is wrong has a permanently unsatisfiable PQ conjunct with no on-chain integrity signal. Non-injectivity instances: trailing handle bytes (recorded), one unread ABI framing word (recorded), half-1 `tr` (NOT in the census; flipping it would ACCEPT), overlapping polynomial offsets (not in the census).
- Failure scenario (liveness): a client-side expansion bug or transport corruption; `setKey` succeeds; the kernel commits to the handle; no signature ever verifies; funds behind the PQ conjunct are frozen. Nothing in the verifier or the kernel detects this at registration.

## C. What the evidence establishes, and what it does not

What it establishes. For one pinned source tree (ZKNoxHQ/ETHDILITHIUM `mldsa-65` @ `4c370bb5`, sha256-pinned per file and checked by `test/Pins.test.ts`), compiled with the vendor's own settings into bytes whose deployed form is reproduced from compiler output plus immutable slots, running on one simulated EVM (EDR, Osaka) with the pinned Keccak helper bound by EXTCODEHASH: the verifier returned the expected verdict on 288 on-chain vectors from four unrelated sources (NIST ACVP, Wycheproof, the pq-crystals KAT, the vendor) plus 52 generated ones, with no inconsistent vector and no disagreement with `@noble/post-quantum` wherever both were compared; the three decoding gates that have historically failed in other implementations — strict z-norm, FIPS Alg. 21 hint canonicality, Decompose/UseHint for gamma2 = (q-1)/32 — are exactly FIPS 204 (my exhaustive models, independent of the vectors); the helper rebuild from the core is byte-exact; a replaced helper is refused; wrong-length inputs are refused cheaply on both entry points; a 32-byte-digest verification costs ~1.54M gas inside the call on this EVM and ten of them fit one Osaka transaction; and the specific behaviours a kernel adapter and a key publisher must handle (40-byte handle normalisation, no canonical-key binding, no integrity signal on a wrong blob, `t1 = 0` acceptance) are reproduced and recorded rather than hidden. I reproduced all 34 tests in 18 s.

What it does not establish. That the 19,617-byte permutation core is Keccak-f[1600] on inputs other than the ~90 it was exercised on; that the 3,179 generated NTT lines are correct beyond the vectors (in particular that every inverse-NTT output lane is canonical, which UseHint silently requires); that any input outside the fixtures — a SampleInBall that exhausts its first block, a non-canonical lane, a structured blob — behaves as FIPS requires; that agreement between ZKNOX and `@noble` is soundness (they could share a defect; the one third-party oracle known to differ, `dilithium_py`, was not run); that the client expansion is correct for keys other than the 52 that verified (the "independent expansion" pins are the same code); that any registration rule proposed in the package stops the degenerate-key class (the `t1 = 0` gate and the PoP do not — A-1); that the publisher design is implementable as written (A-4); that any gas figure holds on Base; or that anything here is ready to be wired to the kernel (no adapter exists, and the kernel's genesis path commits to the key bytes without exercising the verifier, so a mis-published key is a frozen vault). The evidence is conformance on the inputs run, produced carefully and reproducibly; it is not a review of the verifier, and the package's own status line (`PQ_VERIFICATION_CONFORMANCE: PARTIAL_EVIDENCE_UNREVIEWED`) is the right one.
