## 0. Existing behaviour, from source

Every claim inspected at `c67d1439`, not inferred:

- `RecoveryRequest` carries `uint32 challengesUsed; bool active;` (struct, `:127-128`).
- Credential challenge: `recovery.challengesUsed += 1; recovery.active = false;` (`:1206-1208`).
- Fresh initiation explicitly carries the field: `challengesUsed: recovery.challengesUsed,` (`:1177`).
- `rotateCredential` (`:760-801`) references `recovery` **zero** times.
- Successful execution: `delete recovery;` (`:1240`).
- **There are exactly four writes to `recovery` in the kernel:** `:1163` (full
  write at initiation), `:1206` (increment), `:1208` (clear `active`), `:1240`
  (delete). No other site touches it. Co-location's behaviour is therefore
  fully determined by those four sites, and the delete at `:1240` already
  resets the field as a side effect.

## A. Nine histories, two representations

Two kernels compiled in memory — **SEP** (W1's standalone counter, one reset
site) and **COL** (struct, layout and autogenerated getter untouched; field
redefined as epoch-scoped; the existing delete is the reset boundary) — were
driven through identical scripts. After every step both were snapshotted on:
epoch count, stored `active`, `effectiveLive`, installed signer, credential
generation, guardian generation, and the static-call outcome of a credential
challenge, a quorum cancellation, a fresh initiation, and a migration bind.
**Deep equality was required at every step, and held for all nine:**

1. challenge → re-initiate
2. challenge × limit → expire → re-initiate
3. challenge × limit → quorum cancel → re-initiate
4. challenge × limit → ordinary rotation → re-initiate
5. challenge × limit → successful recovery → new recovery
6. successful recovery to identical material → new recovery
7. expiry with no subsequent transaction (three probe instants)
8. three consecutive expiry / re-initiation cycles
9. guardian-set change with a live request (observed identically on both; SD-10
   is not absorbed — the stranding is the same on both and belongs to its own
   record)

**No behaviour differs. Physical separation is not required by the
architecture.** The only field that ever differed was the installed signer at
step 0, and that was a harness artifact — `deployWorld` seeds the original
credential from the world label — corrected by normalising the original signer
to a symbol. It is recorded because a cross-world comparison that is not
normalised on label-seeded material would report a false witness.

## B. SD-9a, re-adjudicated

The questions, answered from the four write sites:

- Is a whole-request `delete` required on credential challenge? **No** —
  `:1206-1208` increments and clears `active`.
- On guardian cancellation? **No** — the probe clears `active` only.
- Is physical cleanup required on expiry? **No** — effective liveness is derived
  from the wall clock; stale bytes carry no authority (Lane W1 §2).
- Is the one whole-request delete on successful recovery exactly the desired
  reset boundary? **Yes** — the Lane W1 §3 boundary, already at `:1240`.

**The defect W called SD-9a is not observable on the kernel as it exists.**
Nothing at `c67d1439` deletes on expiry, so nothing refunds. The refund appeared
only inside a *probe* — a naive sweeper added to test the SD-9b remedy. What is
sustained is narrower and stated precisely:

> **SD-9a (revised): LIFETIME COUPLING.** The kernel provides no lifecycle
> specification distinguishing request-lifetime operations from epoch state,
> so a request-lifetime operation is *free* to reset the epoch — and the
> obvious fix for SD-9b (`delete` on expiry) would do exactly that. This is a
> **remediation hazard and a specification gap**, not a struct-placement
> defect. Storage co-location is not the cause; the missing rule is.

SD-9b, SD-9c, SD-9d and SD-9e remain sustained as recorded in Lane W1 §6.

## C. Getter — `NO_CHANGE_REQUIRED`

The struct, storage layout and autogenerated `recovery()` remain byte-for-byte
as they are. Field 6 keeps its position, type and value; **its meaning changes
from request-scoped to epoch-scoped**, and that is a documentation correction,
not an interface change. All positional tooling — `stateful/invariants.ts:197`,
`stateful/actions.ts:876`, the lane harness `R` map — observes the intended
value unchanged, and the nine-history snapshots read it through exactly that
path. **No second getter or source of truth is created to rename semantics.**

**W1 Option B is withdrawn as unnecessary complexity**, together with the
"breaking getter" flag on W §H item 1. Both were consequences of the
separation assumption, not independent findings.

## D. Stale guardian cancellation — nonce serialisation is sufficient

The structural fact: `initiateRecovery` is the **only** creator of a live
request, and it always consumes a `DOMAIN_GUARDIAN` nonce. So a request R2
cannot exist without consuming the nonce any cancellation pre-signed at that
nonce would need. Live-overwrite refusal (W1) closes the one path on which R1
and R2 could have overlapped. Six executable cases, all on the co-located kernel:

| Case | Before R2 | After R2 |
| --- | --- | --- |
| R1 ends by credential challenge | `NoRecovery`, nonce **unconsumed** | `BadNonce` |
| R1 ends by expiry | `NoRecovery`, nonce unconsumed | `BadNonce` |
| R1 ends by successful recovery | `NoRecovery`, nonce unconsumed | `BadNonce` |
| `setGuardians` between R1 and R2 | — | **`QuorumNotMet`** — the digest binds `guardianGeneration` and `_requireQuorum` runs before `_consume`, so generation binding kills it before the nonce is examined: a second, independent mechanism |
| same block, both orders | — | exactly one transaction succeeds — the initiation — and R2 is live and untouched |
| R2 initiation *fails* | stale cancel is nonce-valid **and still has no live target**; nonce unconsumed | — |

**No request identifier or hash is needed.** The existing nonce protocol plus
the generation binding already in the digest prove non-replay. Adding an ID
would be state without a property behind it.

## E. Candidate P versus Candidate C

| | **P** — separate counter (W1) | **C** — co-located, semantically independent |
| --- | --- | --- |
| semantic correctness | equal (§A) | equal (§A) |
| authority surface | equal | equal |
| accidental-reset risk | lower — a stray `delete recovery` cannot touch the epoch | **higher** — any future `delete recovery` outside `:1240` is a refund; mitigated by the §F mutant and a source comment at the field and at `:1240` |
| ABI | `+recoveryChallengesUsed()` getter, explicit `recovery()` view (Option B) | **unchanged** |
| selectors | +2 | +1 (`cancelRecoveryByQuorum`) |
| storage layout | +1 slot; struct −4 bytes | **unchanged** |
| bytecode | ≈ +100–200 B over C (view + getter) | smaller |
| tooling churn | none, *but only because* Option B is added | none, unconditionally |
| mutation detectability | equal (§F) | equal (§F) |
| reviewer comprehensibility | "obviously not request state" | needs one comment: *this field's lifetime is the epoch's; the delete at `:1240` is the intended reset* |

**Rule applied: prefer the smaller implementation only if the assurance
properties discriminate it equally well.** §F shows they do. **C is the W2
minimal implementation.** Its one real cost — accidental-reset risk — is a
review-and-mutation discipline, not a semantic weakness, and it is not paid for
by visual neatness.

## F. Mutations on Candidate C — all discriminable

| Mutant | Expressed on C as | Killed by |
| --- | --- | --- |
| expiry refunds budget | add a permissionless sweep that `delete`s | history 2 / 7: epoch stays 2 across expiry → re-initiate |
| quorum cancel refunds budget | `delete recovery` in `cancelRecoveryByQuorum` | history 3 |
| ordinary rotation refunds budget | zero the field in `rotateCredential` | history 4 |
| fresh initiation resets budget | `challengesUsed: 0` at `:1177` | histories 1, 2, 3 |
| successful recovery fails to reset | replace `delete` with a field-wise clear that keeps the count | history 5 — and this mutant is *more* natural to express on C |

Each breaks one rule; each has a named killer in the snapshot fields. **Co-location
makes none of them harder to discriminate.**
