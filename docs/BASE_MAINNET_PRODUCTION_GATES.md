# Base Mainnet Production Gates

> ⚠️ **Research prototype. Not audited. Not production custody. Do not use real funds.**
>
> # NO MAINNET REAL FUNDS
>
> **No WalletWall contract may hold real USDC, and no user may be invited to deposit real value, until
> EVERY gate in §2 independently reads PASS, with the evidence named, signed off by the owner named.**
> Partial passes do not accumulate. A gate that was PASS and whose evidence is invalidated by a later
> change (a new kernel generation, a new relayer release, a changed billing product, a new jurisdiction)
> returns to OPEN. This document is the only place a gate's status may be recorded.
>
> Nothing in this repository is a mainnet write path. `scripts/deploy.ts` and `scripts/deploy-simulator.ts`
> refuse chain id `8453` and every other mainnet; that refusal stays until **all** gates pass and is then
> replaced only by a reviewed production deployment procedure, never relaxed in place.

Status legend: **OPEN** (not started or not evidenced), **IN PROGRESS**, **PASS** (evidence linked, signed
off), **STOP** (a stop condition in §4 is live; nothing proceeds until it is cleared). Gates marked
`LEGAL_REVIEW_REQUIRED` are satisfied only by a qualified U.S. legal/compliance review; this repository
records that such a review is required, never its content or conclusions.

As of this document's creation every gate is **OPEN**.

---

## 1. What the gates protect

The claims a real-value launch would be making, each of which a gate makes true or forbids:

1. WalletWall does not independently control or possess user assets (PG-01, PG-02).
2. Asset movement is authorised only by the user's own vault security model (PG-02, PG-06, PG-08).
3. WalletWall relays and pays gas without acquiring withdrawal authority (PG-02, PG-14, SG-05).
4. Billing (optionally through Stripe) is ordinary payment for software and service and is never an
   authorization input (PG-10, SG-06).
5. WalletWall issues no stored value, holds no redeemable balances, exchanges no currency (SG-06, §4).
6. Legal, regulatory, sanctions, privacy, consumer-protection and tax exposure is minimised and **reviewed
   by qualified people**, not declared settled by code (PG-09..PG-13, SG-07).

## 4. STOP conditions

Any of the following, found at any time, sets the lane to **STOP**. Work on the affected area halts until
the condition is cleared by the named decision-maker, and no gate can be marked PASS while a STOP is live.

| Id    | Condition                                                                                                                                                                                                                 | Who clears                                                                  |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| ST-01 | Any design, copy, or code introducing **prepaid gas credits, a gas balance, top-ups, or transferable/redeemable/convertible sponsorship**                                                                                 | owner, only with qualified legal review in hand                             |
| ST-02 | Any proposal to deploy or adapt `WalletWallVault`, `StablecoinVaultSimulator` or `WalletWallMultiSigVault` (the shared-ledger contracts) for real value                                                                   | owner (the custody adjudication must be reopened and re-decided)            |
| ST-03 | Any WalletWall-controlled key acquiring an on-chain role in the production generation: admin, pauser, emergency principal, default guardian seat at or above threshold, policy plane operator, attestor on the spend path | owner + qualified review                                                    |
| ST-04 | Any `PqOnly`-style configuration (an external verifier as sole authenticator) in the production generation                                                                                                                | owner (architecture §4.3a forbids it)                                       |
| ST-05 | Billing-provider state, subscription status, or payment failure becoming an input to any on-chain authorization or to any ability to redirect or seize vault funds                                                        | owner                                                                       |
| ST-06 | Marketing or UI copy containing "quantum-proof", "cannot be frozen", "FDIC", "insured", "guaranteed", "yield", "APY", "interest", "earn", or describing WalletWall as holding, safeguarding or custodying user funds      | owner                                                                       |
| ST-07 | Mock or test verifier artifacts reachable by the production deploy tooling or admissible by the production verifier root                                                                                                  | release owner                                                               |
| ST-08 | A kernel change that introduces `msg.sender` authority, an upgradeable proxy, a mutable factory target, a generic `execute(address,bytes)`, or a module registry                                                          | owner (architecture §5, §20, D8)                                            |

| ST-10 | Any real USDC arriving in any WalletWall-deployed contract before all gates pass                                                                                                                                          | release owner (incident; return path and disclosure)                        |

## 5. Gate dependency order

```
PG-01 (architecture adjudicated)
  └─► PG-02 (no WalletWall authority)  ─► SG-09 (guardian seats)
  └─► PG-03 (chain + USDC pinned)  ─► PG-04 (no mock verifier)  ─► SG-11 (deploy procedure)
  └─► SG-01 (bytes)  ─► PG-06 (invariant/adversarial)  ─► PG-07 (mainnet fork)  ─► PG-08 (audit)
PG-05 (security assumptions)  ◄── PG-06, PG-07, PG-08
PG-14 (relayer runbook)  ◄── SG-04, SG-05  ─► PG-15 (exit path tested)  ◄── SG-02, SG-03, SG-10, SG-12
PG-09 (sanctions review)  ─► PG-12 (legal/compliance review)  ─► PG-11 (jurisdictions)  ◄── SG-06, SG-07, SG-08, SG-13
PG-10 (payments provider)  ◄── SG-06
PG-13 (ToS / disclosures / privacy)  ◄── everything above
```

Review gates (PG-09, PG-11, PG-12) depend on the **architecture being frozen** (PG-01, PG-02): a review
of a moving target is not a review. Conversely, if a review requires an architecture change (ST-09), PG-01
reopens and every downstream gate returns to OPEN.

## 6. What passing every gate does NOT mean

- It does not make the kernel bug-free; immutability makes kernel defects permanent, and migration egress
  is the designed remedy (architecture §2.2, §20).
- It does not remove the guardian-quorum trust root (D1). A quorum of the user's guardians can take the
  vault; this is disclosed, never denied.
- It does not remove issuer risk: the issuer can freeze USDC in any clone.
- It does not remove Base platform risk: sequencer, upgrade keys, and L1 dependencies are external.
- It does not make WalletWall's regulatory status "settled". It means qualified people reviewed the
  architecture as built and WalletWall is acting on their written advice.
- It does not authorise any later change. A new generation, a new chain, a new asset, a new billing shape
  or a new jurisdiction reopens the affected gates.
